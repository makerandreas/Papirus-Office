## 1. UI and interaction findings (user items 1–5, 7)

### F-01 — Viewer and Editor both still draw a per-page `x / y` counter · HIGH · new
**Symptom (user):** in Viewer Mode a small `x / y` sits under *every* page, duplicating the bottom status bar; the same marker also shows in Editor Mode.
**Root cause:** `app/src/main/java/com/example/modules/inky/LayoutDrivenDocumentRenderer.kt:174-182`
```kotlin
Box(modifier = Modifier.fillMaxSize(), contentAlignment = Alignment.BottomCenter) {
    Text(text = "${page.pageNumber} / ${computed.pages.size}", fontSize = (9 * zoomScale).sp, ...)
}
```
This `Box` is a sibling of the page's element `Column` inside **every** page card, in **both** modes (`isEditMode` is not consulted). It bypasses the P1-1 unified bar entirely (`InkyModule.kt:2368-2470`), leaving two page counters on screen.
**Fix direction:** delete the per-card marker; the unified bar is the single source of truth (matches the P1-1 decision recorded in audit-003).

### F-02 — Viewer "Edit" FAB overlaps the bottom status bar · HIGH · new
**Symptom (user):** the Edit FAB covers the word/char counter / status bar.
**Root cause:** `InkyModule.kt:4170-4205` — `Box(Modifier.fillMaxSize().padding(16.dp), contentAlignment = Alignment.BottomEnd)` wrapped around the FAB. It is composed *after* the status bar, so it draws on top of it and eats its 56 dp corner, including the tap target for Go-to-Page.
**Fix direction (DESIGN.md compliant):** the comment asks "what does this serve?" — an always-visible FAB is redundant with the bottom sheet's first icon and the toolbar hub. Either (a) move the edit affordance **into** the status bar as a 48 dp icon slot, or (b) keep the FAB but give the status bar a matching trailing inset so the two never overlap. Option (a) is the M3 Expressive answer: FAB is for the primary *creation* action, not for mode switching.

### F-03 — Word/character counter not optically centred · MEDIUM · new
**Root cause:** `InkyModule.kt:2400-2456` — the bar is a `Row` with `Arrangement.SpaceBetween`; the left slot is a `Row` (icon + page text) and the right slot is a 3-button zoom cluster in Editor and a bare `Spacer(32.dp)` in Viewer. Centre-of-row ≠ centre-of-screen in either mode.
**Fix direction:** three equal-weight slots (`Modifier.weight(1f)` × 3, `Alignment.Center` for the middle, `Alignment.End` for the right) so the counter is centred at any content length; apply the same to the Viewer variant.

### F-04 — After opening every bottom-sheet deck the keyboard cannot be summoned · HIGH · new
**Symptom (user):** opening all Standard Bottom Sheet elements, then pressing the keyboard icon or tapping the document does nothing; Viewer → Editor restores it. Repro on a **newly created** document.
**Root cause (two, both real):**
1. `InkyModule.kt:117` declares the only `FocusRequester`, and it is attached to exactly one node: `InkyModule.kt:2354`, the **Web-View** `BasicTextField`. In the normal path the editor is `LayoutDrivenDocumentRenderer`, which owns a *separate* `HashMap<Int, FocusRequester>` per element (`LayoutDrivenDocumentRenderer.kt:66`). The keyboard hub button (`InkyModule.kt:2758-2767`) therefore calls `requestFocus()` on an unattached requester — swallowed by `try { } catch (e: Exception) { }` — and then `keyboardController?.show()`, which cannot raise an IME without a focused editor.
2. `LaunchedEffect(showBottomBar)` force-clears focus when a sheet opens (`focusManager.clearFocus(force = true)` + `keyboardController.hide()`), and nothing re-arms a field on sheet close. Tapping the viewfinder then has no focused node to take the IME, and the newly created document's first field is never focused after the sheet closes.
**Fix direction:** give the renderer a focus bridge (expose "focus the element under the caret / first editable element"), attach the hub button and the sheet-close path to it, and let the document tap hand focus to the tapped field. Remove the silent `catch`.

### F-05 — Viewer text is selectable but the FCT never appears · HIGH · new
**Symptom (user):** selection works in Viewer, but neither long-press nor dragging the water-drop handle raises the FCT. Tap-and-hold works on a fresh document in Editor Mode.
**Root cause:** Viewer renders `ParagraphSelectField` — `BasicTextField(readOnly = true)` (`LayoutDrivenDocumentRenderer.kt:385-445`). It has **no `FocusRequester`** and never calls the toolbar: the only places `PapirusTextToolbar` is shown are `TextToolbar.showMenu(...)` callbacks from an *editable* field, and the explicit `customTextToolbar.show(rect)` entry point (`PapirusTextToolbar.kt:77`) is called **nowhere** in `InkyModule.kt` (grep: `hide()` at 7 sites, `show(` at none). The selection state does reach the app (`onViewerSelectionChange → docBodyText`), so the data is available — only the presentation trigger is missing. This is a regression of the S5 Viewer-selection design: the range is exposed but the toolbar was left entirely to the platform, and the read-only path in this configuration demonstrably does not raise it (the field is also outside the edit path that owns every other `showMenu` caller). Whether Compose *intends* to fire the platform menu here cannot be checked in this sandbox (Compose sources are not vendored and there is no JDK), so Plan 2 must confirm with a log on device and, either way, add the explicit bridge below — it is correct independently of what the framework does.
**Fix direction:** in `ParagraphSelectField`, `LaunchedEffect(localValue.selection)` → when non-collapsed, resolve the field's `boundsInWindow` and call `customTextToolbar.show(rect)`; keep `hide()` on collapse. Verify on device that handle drags fire the same effect (they do update selection, so they will).

### F-06 — 100 % zoom is not fit-to-screen · MEDIUM · new
**Symptom (user):** at 100 % the page is not fitted to the screen.
**Root cause:** `LayoutDrivenDocumentRenderer.kt:117` — `val cardWidthDp = 320f * zoomScale`. The page is a fixed 320 dp wide regardless of the viewport (a Realme C3 is a 320 dp-wide device, so card + 48 dp padding overflows and forces horizontal scrolling). Nothing computes `fitWidth = viewportWidth / page.widthDp`.
**Fix direction:** introduce a single transform (this is F-1 from `plan-2026-09-22`): `cardWidthDp = page.widthDp * zoomScale * fitScale`, where `fitScale = viewportWidth / page.widthDp`. Then 100 % means "page width = viewport width", the way M365/Word mobile behaves, with 25–400 % preserved as multipliers.

### F-07 — Image render delay ≥ 500 ms; images sometimes never appear · HIGH · new
**Symptom (user):** images take ≥ half a second to appear when opened via Start Center → Recents; sometimes they never load (both formats).
**Root causes (four, cumulative):**
1. **Artificial delay.** `InkyModule.kt:1092-1103` (`runDocumentLoading`) hard-codes `delay(500); delay(500); delay(400)` — 1.4 s of theatre before the document is even assigned.
2. **Evictable media.** `DocxImageExtractor.kt:33` extracts into `File(context.cacheDir, "docx_media_<sha>")`. Android trims `cacheDir` under memory pressure (this is the Realme C3 class of device); a trimmed directory leaves `OfficeParsedDocument.elements` holding `File` handles that no longer exist, and the renderer degrades to the `[Image]` placeholder (`LayoutDrivenDocumentRenderer.kt:448-470`) with no recovery path.
3. **No placeholder/geometry.** `DocxEmbeddedImage` uses Coil's `AsyncImage` with no `placeholder`, no `size()`, and no `crossfade(false)`; the first frame is blank until decode completes.
4. **Re-extraction per open.** The Room cache stores only `plainText` (`DocumentCacheEntity`), so every Recents open re-parses and re-extracts media, which is exactly the ≥500 ms window the user sees.

## 2. Sample-6 ODT findings (user items 8–14)

Composition of `tests/inky/Sample-6.odt` (`/tmp/s6o`: `content.xml` 176,805 chars): **322** `text:p`, **45** `text:h`, **451** `text:span`, **115** `text:list`, **180** `text:list-item`, **1** table (6 rows × 30 cells), **3** `draw:frame` + 3 `draw:image`, **1** `text:table-of-content`, **5** `text:section`.

| ID | User finding | Verdict | Root cause |
|---|---|---|---|
| **F-08** | Font size renders correctly (12 pt) | **Confirmed correct — by accident** | `Normal` carries `style:font-name="Times New Roman"` + `fo:font-size="12pt"`, and `ParagraphStyle.fontSizeSp` defaults to `12f`, so a *failed* style lookup is indistinguishable from a correct one. |
| **F-09** | Font *style* (Times New Roman) not rendered | **Confirmed** | `StyleResolver.resolveParagraphStyle` returns the cascaded `ParagraphStyle`; display goes through `OfficeRuns.fontFamilyFor("Times New Roman") → FontFamily.Serif`, i.e. the platform's generic *serif* (Noto Serif), not a Times-metric face. The bundled Liberation Serif in `assets/fonts` (`FontProvider` already extracts it to `/storage/emulated/0/Fonts`) is never used for display or for metrics. Family identity is therefore lost even though the *category* is right. |
| **F-10** | Paragraph formatting near-perfect, needs Writer-Guide tweaks | **Partially confirmed** | `applyParagraphProperties` reads **only** `fo:text-align` (`SvXMLImport.kt:150-152`). Ignored: `fo:line-height` (Normal = 116 %), `fo:margin-top/bottom` (0.282 cm after every paragraph), `fo:text-indent`, `fo:margin-left`, `fo:keep-with-next` (Heading 1/2 declare `always`), `fo:break-before` (`PP19` declares `page`). |
| **F-11** | Table does not load properly | **Confirmed** | Parsing is fine (`OdfTableContext`, `SvXMLImportContext.kt:418-450`), rendering is not: `LayoutEngine` allots `rows * 35 + 10` units (`LayoutEngine.kt:377-380`) with **no** regard for `w:tblGrid`/`table:table-column` widths, font size, or cell padding, and `RenderTable` draws every cell at a hard-coded `10.sp` (`LayoutDrivenDocumentRenderer.kt:497-521`, size at `:514`). A 30-cell 5-column table becomes 5 equal 10 sp columns and clipped text. Column widths are parsed nowhere. |
| **F-12** | Bullets render but at a different font size | **Confirmed** | `OdfListItemContext` hard-codes `"• "` / `"◦ "` (`SvXMLImportContext.kt:373-380`) with no style and no size, and `toOfficeDocument()` bakes the bullet into the paragraph text with a **single default run** (`OfficeDocument.kt:363-368`), losing the list item's runs. The bullet is then rendered with whatever paragraph style the container resolved, and the item text with the 12 sp default, so sizes diverge. |
| **F-13** | Multilevel list not rendered (`BAB II`, `2.1`) | **Confirmed** | `SvXMLImport` never parses `text:list-style` / `text:list-level-style-number`; `OdfXmlToken` has no token for them. Sample-6's headings and list paragraphs carry `style:list-style-name="Makalah_20_Default"` (level 1 `num-prefix="BAB "`, `display-levels` 1; deeper levels display `2.1`), and the `"BAB"` literal appears **0** times in the body text — the numbering exists only as a list definition. | **F-15** | Character formatting correct | **Confirmed for body, lost for headings** | `OdfHeadingContext` (`SvXMLImportContext.kt:228-269`) accumulates text only; `OfficeDocumentElement.Heading` has no `runs` field; `toOfficeDocument()` writes `runs = emptyList()` (`OfficeDocument.kt:355-362`). Any bold/italic/colour inside `<text:h>` is discarded, and the renderer re-synthesises the heading as a plain paragraph with an empty run list. |

## 3. Sample-6 DOCX findings (user items 15–19)

Composition of `tests/inky/Sample-6.docx` (`/tmp/s6d`): `word/document.xml` 123,848 chars — **371** `w:p`, **1** `w:tbl` (5 `gridCol` 1647/1443/2282/1642/2011 dxa, `tblW` 9025), **3** `w:drawing`, **45** `w:hyperlink`, **1** TOC field (`w:instrText`), **5** `w:sectPr` + 5 footers, **202** `w:pStyle`, **133** `w:numPr`, **2** page breaks. `w:docDefaults` = Aptos 12 pt (`w:sz` 24), `after=160`, `line=278 auto`, `jc=both`. Heading semantics live on `para1…para9` (name `heading N`) and their character twins `char1…char3` (Aptos Display, `w:sz` 40/32/28 half-points = 20/16/14 pt).

| ID | User finding | Verdict | Root cause |
|---|---|---|---|
| **F-16** | Heading font size wrong | **Confirmed** | The DOCX branch tags headings with `styleName = "Heading $headingLevel"` (`OfficeDocumentParser.kt:1064-1074`), which is **not** the DOCX style id (`para1`). `extractDocxStyles` keys `ParagraphStyle` by the DOCX id and — decisively — `DocumentStyles` for DOCX is built as `ParagraphStyle(name = meta.name, parentStyleName = meta.basedOn)` with **no size, no weight, no family** (`OfficeDocumentParser.kt:1196-1204`). So every heading misses the map and lands on the legacy fallback 24/20/16 pt bold (`LayoutEngine.kt:60-80`) instead of 20/16/14 pt Aptos Display, and body text lands on `resolveParagraphStyle(null) → 14 sp` instead of docDefaults' 12 pt. |
| **F-17** | Tables not rendered | **Confirmed (degraded render, not a parse failure)** | `w:tbl`/`w:tr`/`w:tc` *are* collected (`OfficeDocumentParser.kt:940-955`, `1046-1082`), but the resulting `OfficeTable` loses `w:tblGrid` widths and `w:tblW`, is paginated at a flat `rows * 35 + 10` units, and is painted at a fixed `10 sp`. The 5-column table is squeezed into equal columns and overflows its card, which reads as "not rendered". `gridSpan`/`vMerge` are unhandled. |
| **F-18** | Image size differs from the ODT counterpart | **Confirmed** | The active DOCX branch creates `ImageElement(imagePath, imageFile, name)` and **never** reads `<wp:extent cx cy>` (`OfficeDocumentParser.kt:1000-1016`). There *is* an extent reader, but it lives in the dead legacy path: `DocxDocumentParser.parseDocxFile` (reachable only for non-zip files, since `parseDocument` routes every zip to `OfficeDocumentParser`) fills `extentsMap["default"]`, which `parseDocument` then drops — so `DocxParseResult.imageExtents` is always empty, `InkyModule.docxExtents` (`InkyModule.kt:204`, 5 assignments, **0 reads**) is dead state, and no renderer ever sees an extent. `LayoutEngine` reserves the default 180 units of height and the renderer falls back to `1905000 × 1428750` EMU. The ODT path *does* read `svg:width`/`svg:height` (`OdfFrameContext.parseDimensionToDp`), so the same picture is 292 dp from `.odt` and 200 dp from `.docx`. Both samples declare identical geometry (`7.735 cm` ↔ `2784475 EMU`). |
| **F-19** | TOC renders imperfectly | **Confirmed** | DOCX text events are accumulated regardless of container, so TOC entry text *does* appear — but with no leader tabs (right-aligned page numbers become a stray `\t`), `w:instrText` field code is not suppressed, and the entries inherit the 14 sp body default instead of `TOC 1/2/3`. |
| **F-20** | Character/paragraph formatting "prematurely" | **Confirmed, and worse than it looks** | Run flags are set on `w:b` / `w:i` / `w:u` **without reading `w:val`** and are only reset at `</w:p>` (`OfficeDocumentParser.kt:906-916`, `1085-1100`). A `w:b` inside one run therefore bolds every following run of that paragraph; `w:b w:val="0"` bolds; `w:sz`, `w:rFonts`, `w:color`, `w:spacing`, `w:ind`, `w:jc`, `w:pBdr` are never read; `currentRuns` is filled but never used for the paragraph it belongs to (the paragraph falls back to one flat `TextRun(paraText, isBold, isItalic, isUnderline)`); `w:lastRenderedPageBreak` is treated as a hard page break, which is a *rendering* hint, not authored structure. |

## 4. Cross-cutting root causes (the "why" behind the page counts)

### 4.1 Measurement fudge — the single biggest driver of F-21
`LayoutEngine.kt:154`:
```kotlin
setPaintTextSize(style.fontSizeSp * 2.5f) // rough dp-to-px scaling factor for virtual measuring
```
`PageStyleSpec` works in **layout units at 96 per inch** (`OdfLength`, `OpenXmlUnits`), where 12 pt text is `12 × 96 / 72 = 16` units. Measuring it at `30` units makes every line ~1.9× too long, so paragraphs wrap ~1.9× sooner and are ~1.9× taller. That alone explains most of 21 → 65/88, and it also corrupts the image extents used for pagination.

### 4.2 Fixed 12-unit gap, no paragraph spacing
`LayoutEngine.kt:107/331` — `currentY += h + elementGapDp` for **every** element. Sample-6.odt has 547 textual elements; the flat gap contributes ≈ 6,500 units ≈ 7 A4 pages of pure whitespace, and it replaces (rather than replaces *with*) the declared `fo:margin-bottom="0.282cm"` / `w:spacing after=160`. Nothing collapses margins, nothing honours `fo:break-before="page"`, `fo:keep-with-next`, or `w:pageBreakBefore`.

### 4.3 Two style models, one of them empty
ODF: rich `OdfStyleInfo` cascade incl. default-style (`SvXMLImport.cascadeStyle`) → but spacing/indent/line-height/keep props are never captured, and character styles deliberately skip the default-style (F-3, correct).
OOXML: `DocxStyleMeta` keeps `name` + `basedOn` + heading flag only → `ParagraphStyle` has no size/weight/family. The two formats therefore reach the renderer with **different amounts of truth**, which is exactly the user's observation that DOCX feels further from the original than ODT.

### 4.4 Rendering is decoupled from measurement
`LayoutEngine` measures with an Android `Paint` (real device) while the renderer draws Compose `sp` text with `fontFamilyFor(...)`. Any disagreement in size, family, or line height shows up as text that overflows its reserved box or leaves a gap — the user's "premature formatting" impression.

### 4.5 Page count sanity targets
* Sample-6: M365 Copilot = **21 pages**. Papirus = **65 (ODT)** / **88 (DOCX)**, i.e. 3.1× / 4.2×.
* Sample-5 baseline: M365 = **18 pages**; CI window today is `12..30`. After 4.1–4.2 land, the window should tighten to **18 ± 3** and be enforced.

## 5. Secondary observations (not in the user's list, but found while tracing)

* **O-01 · Save path can destroy DOCX content.** `DocxDocumentParser.saveDocument(file, document)` regenerates `word/document.xml` from `OfficeDocumentElement`s and replaces images with `"[Image: path]"` text while copying every other zip entry untouched. Until images and styles survive the round trip, a save from this build is lossy. Same class of risk for `content.xml` on the ODT side.
* **O-02 · `w:lastRenderedPageBreak` is not authored structure.** Treating it as a page break (and appending `--- Page Break ---` to the plain text) both inflates pagination and pollutes the editable text that `DocumentTextMerger` later writes back.
* **O-03 · Section coverage.** `text:section` (5 in Sample-6.odt) works only because the base context happens to recurse; `style:master-page-name` (`Chapter2` on `PC77`) is ignored, so chapter master pages never switch.
* **O-04 · 45 hyperlinks in Sample-6.docx** produce visible text but no link affordance; on the ODT side the same content is silently deleted (F-14).
* **O-05 · No `text:numbered-paragraph` support** (`ODF 1.4 Part 1 §5.3.2`), which LibreOffice writes for numbered headings.
* **O-06 · `assets/hyphenation` ships only `en_us.hyph`** while Sample-6 declares `fo:language="id"`; hyphenation stays off by default (S6 decision) so Indonesian text wraps whole-word, adding lines.
