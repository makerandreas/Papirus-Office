## 1. General experience — the three “small UX, big signal” items

### 1.1 Inky Viewer Mode: the elusive page marker

**What you saw:** a tiny `x / y` centred under each page card, repeated per page.

**What you asked for (and why it is right):** a single elongated status bar, **only in Viewer Mode**, pinned at the viewport bottom:

* left: `Page x–x of y` (continuous-scroll range) or `Page x of y` (single-page viewport),
* right: `N words, M characters`.

**What the code does today — `InkyModule.kt`:**

* ~L2430-L2475 — status bar with `Page x of y` + `wordCount ... chars` + zoom controls exists, but gated by `if (isEditMode)` — i.e. **only in Editor Mode**, not Viewer.
* Viewer footer is rendered *inside* each `Surface` card (`${pageIndex+1} / $totalDocPages` at L≈835) — hence the per-page repetition.
* `totalDocPages` comes from `documentLayout.pages.size` (LayoutEngine) while Editor paginated sheets use `pagesList = partitionTextToPages(docBodyText.text)` — two unrelated counts.

**Design fit (DESIGN.md dial ENERGY 2 / RHYTHM 1 / MOTION 3):** a persistent Viewer status bar aligns with “uniform, predictable, document-grid consistency” (RHYTHM 1) and with Reader/Minimal Viewer pattern used in Slidia/Pagella. Material 3 Expressive calls this a *tonal bottom bar* (`surfaceVariant`, 48 dp touch, `labelSmall`).

**Suggestion before coding (P1, 1–2 days):**

* Introduce `ViewerStatusBar` composable: `Surface(tonalElevation=2.dp, color=onSurfaceVariant 0.8f)` mirroring the Editor bar but with distinct copy and without zoom controls (zoom stays in Editor; Viewer gets Fit-Width toggle only).
* Derive its page range from the visible-viewport rect, not `currentDocPage`. Needed inputs already exist: `viewportCoordinates`, `bodyTextFieldCoordinates`, `pageBoxCoordinates`. Compute `visiblePageRange: IntRange` via `viewportCoords.localPositionOf(...)` against each `PageLayout.bounds`.
* String: add `viewer_status_page_range` — `"Page %1$d–%2$d of %3$d"` and `"Page %1$d of %2$d"` — keep in `values/strings.xml` (en_US) per `AGENTS.md`.
* Remove the per-card `${pageIndex+1} / y` `Row` from `LayoutDrivenDocumentRenderer` path when `!isEditMode`.

### 1.3 GitHub: Nightly entry never updates, `universal` / `x86_64` leak

**What you saw:** every push rebuilds the APKs, but the `Papirus Office Nightly Build` entry on Releases stays at a 2-week-old timestamp/body; old `universal` and `x86-64` artefacts remain.

**Root causes in `.github/workflows/build.yml`:**

1. `softprops/action-gh-release@v3` with `tag_name: "nightly"` and `prerelease: true` **without** `make_latest: false`, `generate_release_notes: false`, `append_body: false`, or `body:`. On softprops v3 the `name` + `body` fields are *not* auto-refreshed when the tag already exists — the body freezes at creation time. Hence the stale description.
2. `files:` globs only the two split APKs (`app-arm64-v8a-debug.apk`, `app-armeabi-v7a-debug.apk`) — correct. But any previous `universal-*.apk` assets already attached to the `nightly` tag are never removed (softprops does additive uploads by default). They persist even though `assembleDebug` no longer produces a universal artefact.
3. The scheduled `cron: '0 2 * * *'` + `workflow_dispatch` + `push` all hit the **same** `nightly` tag; concurrent runs race for the tag ref (softprops `v2` → `v3` migration note in `audit-002` partially mitigated Node 20 warnings but not this).

**Impact:** users on the Nightly channel download a stale description that undersells recent fixes; extra artefacts bloat the release (≈ 30 MB each).

**Suggestion before coding (P0 — release hygiene, ≤1 hr):**

```yaml
- name: Drop Papirus Nightly Release (Debug APK Only)
  uses: softprops/action-gh-release@v3
  with:
    tag_name: nightly
    name: Papirus Office Nightly Build — ${{ env.APP_VERSION_NAME }}
    body: |
      Automated nightly from `${{ github.sha }}` on `${{ github.ref_name }}`.
      Built ${{ env.APP_VERSION_NAME }} (code ${{ env.APP_VERSION_CODE }}) with JDK 17.
      APKs are split per ABI: arm64-v8a + armeabi-v7a (no universal). Install the one matching your device.
    prerelease: true
    make_latest: false
    generate_release_notes: false
    append_body: false
    fail_on_unmatched_files: false
    files: |
      app/build/outputs/apk/debug/app-arm64-v8a-debug.apk
      app/build/outputs/apk/debug/app-armeabi-v7a-debug.apk
```

*Optional purge:* add a preceding step `gh release delete-asset nightly app-universal-*.apk --yes` (gh is pre-authenticated) guarded by `gh release view nightly --json assets --jq`.

Do **not** switch to `actions/upload-artifact` for nightlies — nightly semantics are intentionally “one moving release tag”.

## 3. Inky fidelity — the Viewer/Editor split brain (the central P0)

### 3.1 What you reported

* Viewer (via SAF `Files` picker, Sample-5): images near-correct, heading sizes near M365 — good ODF start.
* Editor after toggle: *unformatted plain text*, image vanishes (Navigator still lists it), `BasicTextField` loses heading size/alignment.
* FCT cannot be summoned by tapping the “waterdrop” handle or long-pressing text in **either** Viewer or Editor for imported docs — but FCT *does* work in a freshly created Papirus doc in Editor.

### 3.2 Why it happens — single root cause, three symptoms

**Root cause:** two independent render+edit stacks.

| Mode | Render stack | Edit model | Style fidelity |
|---|---|---|---|
| **Viewer** (`!isEditMode` Branch L≈640) | `LayoutDrivenDocumentRenderer` ← `activeLayoutDocument` ← `LayoutEngine(documentLayout, OutlineEngine)` | Not editable; navigable | Heading sizes via `StyleResolver`, image via `DocxEmbeddedImage` and `extractedImages` map |
| **Editor** (`isEditMode` Branch L≈685) | `partitionTextToPages()` → `List<String>` → per-page `BasicTextField` (L≈725) with a *single* global `activeFontFamily/Size/Bold/Italic` (L≈745) | `docBodyText: TextFieldValue` (plain string) merged back via `DocumentTextMerger.mergeEditedText()` lazily | **No per-run styling** — entire page inherits toolbar state; `docxImages` only shown once via `firstOrNull()` on page 0. |

Consequences:

1. **“Unformatted” Editor** — expected: `docBodyText` is lossy. The 61/73-page plain-text view cannot carry `<text:span text:style-name=…>` runs.
2. **Image vanishes** — `DocxEmbeddedImage` renderer is not wired in Editor; images live in `OfficeDocument.body.elements` (`ImageElement`) but `BasicTextField` cannot host composables. Navigator still sees them because it indexes `documentLayout.elementPageIndex` (which tracks `ImageElement`s even when hidden).
3. **FCT missing on imported docs** — FCT is provided via `CompositionLocalProvider(LocalTextToolbar → customTextToolbar)` and triggered by selection handles inside `BasicTextField`. Viewer never creates a `BasicTextField` (only `Text()` calls), so there is no selection handle to press. Editor’s paginated `BasicTextField`s (per-page) each hold a *separate* `TextFieldValue` (`pageTextVal`) that never propagates selection back to the `customTextToolbar`’s `rectState`. Fresh docs happen to work only when the single-sheet fallback (`!isWebView && pagesList.size>1` is false) is taken.

### 3.3 ODF 1.4 gaps behind “almost right” headings

`StyleResolver` in `LayoutEngine.kt` already maps `Heading 1/2/3 → 24/20/16 sp` — hence “similar to M365”. But `SvXMLImport`/`SvXMLImportContext` only parse:

* `style:name`, `style:family`, `style:parent-style-name`, `default-outline-level` → `OdfStyleInfo` (SvXMLImport.kt ~90).
* Text properties extracted: `fo:font-size`, `fo:font-weight`, `fo:font-style` in `OdtDocumentParser` contexts — *not* in the newer `SvXMLImport` path.
* Missing for Writer parity (per `sources/OpenDocument-v1.4-part3-schema.html`): `fo:font-family`, `style:font-name`, `fo:text-align`, `fo:margin-left/right`, `fo:text-indent`, `fo:line-height`, `fo:background-color`, `style:page-layout` (`fo:page-width/height`, `fo:margin`), and `number:style-name` for numbering.

So headings round-trip structurally but typographically collapse to the three-size heuristic.

### 3.4 Suggested fix order (do not intermix)

**P0 — Unify the stacks (2–4 days, one PR per step suggested):**

1. **Retire `partitionTextToPages` for layout.** Keep it only for *unit-test stubbing*; Editor must render from `documentLayout.pages` (same as Viewer). Editor becomes `LayoutDrivenDocumentRenderer` + overlay `BasicTextField` per `PageElementLayout` with injected cursor, not a re-chunked string list.
2. **Promote `OfficeTextRun` to first-class.** `OfficeDocument.body.elements` already carries `List<OfficeTextRun>` (bold/italic/underline, future font/color). Teach `SwDocEngine` + `DocumentTextMerger` to round-trip runs, and make Editor’s text composable consume `AnnotatedString` with `SpanStyle` instead of a single global `textStyle`.
3. **Image interleave.** Replace the `firstOrNull()` image hack (L≈695) with `for (elem in documentLayout.pages[pageIndex].elements) when (elem.element) is OfficeImage/ImageElement → RenderImage(...)` — same loop Viewer uses. Gate via `InlineImagePlugin`-style composable inside the paragraph column.
4. **FCT for Viewer.** Wrap Viewer paragraphs in `SelectionContainer` (Compose 1.6) or a custom `ClickableText` with `onTextLayout` + `pointerInput(detectTapGestures)` that computes `rectState` via `TextLayoutResult.getBoundingBox`. In Editor, supply a *single* `TextFieldValue` (not per-page splits) backed by `documentLayout` heights.

**P1 — ODF style fidelity (1–2 days after P0 lands):**

* Extend `SvXMLImportContext` parsing: handle `style:text-properties` (`fo:font-family/name/size/weight/style/color`, `style:text-underline-style/color`), `style:paragraph-properties` (`fo:text-align/margin/indent/line-height/background-color`, `style:page-layout-name`), and `style:graphic-properties` for images.
* Thread `PageLayout` dimensions from `style:page-layout` (`fo:page-width` `fo:page-height` `fo:margin-*`) into `LayoutEngine(pageWidthDp, pageHeightDp)` rather than hardcoded `816 × 1056`.
* Add `tests/inky/Sample-5.odt` snapshot test that asserts heading font-size within ±1 pt of LibreOffice’s computed `fo:font-size`.

All five map directly to your final wish list: *font style, precise font size, alignment, paragraph/character formatting, page breaks, objects, per ODF Part 3*.

## 4. Pagination: why 18 → 61 (DOCX) / 73 (ODT)

**Repro:** Sample-5 in M365 = 18 pages; Papirus Viewer = 61 (DOCX) / 73 (ODT). The *same* document yields *two* wrong answers, which is diagnostic.

**Three divergences compounding:**

1. **Dual pagination engines** — Viewer uses `LayoutEngine(pageWidthDp=816, pageHeightDp=1056)` with `place()/flushPage()` heuristics; Editor paginated fallback uses `partitionTextToPages(charsPerLine=75, defaultLinesPerPage=46)` — a 46-line heuristic unrelated to A4 metrics. DOCX path hits both; ODT path hits only LayoutEngine — hence the 12-page split between DOCX and ODT.
2. **No page-layout awareness.** ODT `content.xml` + `styles.xml` declare `style:page-layout` with `fo:page-width`, `fo:page-height`, `fo:margin-top/bottom/left/right`. Today `LayoutEngine` ignores them (hardcoded 816×1056). Sample-5 uses A4 + narrow margins → Papirus reserves 50 px top + 60 px bottom + 12 px inter-element gap → ~15 % less usable height → ~3× more pages.
3. **Naïve text metrics.** `LayoutEngine.layoutParagraph()` measures with `Paint.measureText` on a single `StyleResolver` font size (no `FontLoader`/`FontCacheManager` metrics, no hyphenation, no `fo:line-height` or `fo:widows/orphans`). Line wrapping is `word.split(" ")` — so long Indonesian compound words force extra lines. `hyphenation/en_us.hyph` is bundled in `assets/hyphenation` but never consulted.

**Suggestion before coding (P0, tied to §3.4):**

* Single pagination: `LayoutEngine` becomes the sole paginator for Viewer *and* Editor. Retire `partitionTextToPagesFromText` from UI; keep only for offline word-count estimation if needed.
* Parse `style:page-layout` in `SvXMLImport` and propagate to `LayoutEngine` construction inside `InkyModule`. Fall back to 816×1056 only when absent.
* Replace word-wrap with `TextLayoutManager` line-break + `hyphenation` dictionary lookup (already in assets). Gate behind `PapirusConfigManager` feature flag if needed for C3 memory.
* Add an instrumented assertion: for `tests/inky/Sample-5.*` assert `documentLayout.pages.size` is within `18 ± 3` after fix — makes the 61/73 regressions CI-visible.

## 5. Images: SAF open shows image, Recents reopen shows `[Image]`

**Repro:** open via `Start Screen → Files → SAF` → image renders. Reopen the same file via `Start Screen → Recents` → placeholder `[image]` / `[Image]` string only. Navigator still lists the image — so the *index* knows it.

**Why — two interacting bugs:**

1. **Cache key is filename, not file identity.** `DocxImageExtractor` caches under `context.cacheDir / "docx_media_${file.nameWithoutExtension}"` and `extractedImages` is keyed by `imageName` / full path. SAF open uses `OpenedDocumentStore.persistFromUri()` which copies to a cache file named via `DISPLAY_NAME` (often `document.odt`). Recents stores the *original* `absolutePath` string; on reopen the parser re-extracts to `docx_media_document` (generic) and collisions overwrite. If the SAF copy was deleted by `DocumentCacheCleanupWorker` (see `PHASE6_MEMORY_PLAN` caps), the map is empty on second open.
2. **`RenderImage` fallback is strict.** `LayoutDrivenDocumentRenderer.RenderImage` tries `imageFile`, then `extractedImages[imagePath]`, then `substringAfterLast('/')`. If the ODT’s `<draw:image xlink:href="Pictures/100000010…jpg">` does not match any key (because extractor sanitized the name to `100000010....jpg`), it falls back to `Text("[Image]")`. Viewer path keeps the `ImageElement.imageFile` pointer (from extractor) so it survives even when `extractedImages` is empty — but Editor’s `firstOrNull()` path discards it.

**Suggestion before coding (P1, 0.5 day):**

* Re-key image cache by `file.toCacheKey()` = `sha1(path + lastModified + length)` or by `content://` URI hash, not `nameWithoutExtension`. `OpenedDocumentStore` already knows the URI — persist the hash alongside the Recents entry (`InkyDocumentMetadataEntity.filePath` should be the hash-addressed copy, not the raw path).
* In `OfficeDocumentParser.extractXmlContent` + `DocxImageExtractor`, store *both* the sanitized name and the raw href (and lowercased variant) — already partially done (`extractedImages[name] = file`) but ensure the raw `Pictures/...` key is always written (presently gated on `if (!outputFile.exists())` reuse).
* `RenderImage`: when `resolved == null`, attempt `context.contentResolver.openInputStream(uri)` as last resort before the placeholder, and show a broken-image icon with retry rather than text.
* Add a small regression test: open Sample-5 via SAF path, close, reopen via Recents path, assert `index.images.isNotEmpty()` and `extractedImages.containsKey(Pictures/…)` remains true.

## 6. Navigation: from `Partial` to `PASS` — locale fix

**Repro:** Sample-5 (language Indonesian, `office:language`-derived) shows Navigator categories in Indonesian (`Judul 1`, `Tabel1`, `Gambar1`) even though the Papirus app language is English. You expect English strings when the app is English, regardless of document language.

**Why:**

* `NavigatorStringCatalog.detect(document)` (NavigatorStringCatalog.kt:115) **intentionally** prefers *document evidence* (any `Judul`/`Tabel`/`Gambar` token) over the document’s `metadata.language` default (`en-US`). If the file contains even one `Judul 1` style, it returns `INDONESIAN` — no app-locale input is consulted.
* `DocumentIndexEngine` (L:76) calls `detect(document)` and alone decides auto-names (`DocumentIndexModels` prefixes). `UniversalNavigatorSheet` then displays those names directly via `stringResource` fallbacks — there is no override that respects the device/app locale (`LocalConfiguration` / `AppCompatDelegate`).
* `NavigatorStringCatalogTest.indonesianJudulStylesIndexEvenWhenMetadataIsEnglish` *asserts* this behavior — so the current design is deliberate and tested, just not what you want for Viewer UX.

**Two legitimate interpretations:**

* **LibreOffice semantics:** Navigator reflects the *document’s* authoring language (so an Indonesian document surfaces `Gambar`, even in an English UI) — faithful to desktop.
* **Mobile-app semantics (your request):** UI language dominates — Navigator is chrome, not content, so it speaks the *user’s* language.

**Suggestion before coding (P2, small, but decide policy first):**

* Introduce `PapirusOfficeOptionsScreen → Appearance → Navigator language: [Follow document | Follow app language]` (default: `Follow app language` after this audit). Persist in `InkyPreferences` / `PapirusConfigManager`.
* Change `DocumentIndexEngine` ctor to `DocumentIndexEngine(document, preferAppLocale: Boolean)` and thread `Locale.getDefault()` or `context.resources.configuration.locales[0]`.
* When `preferAppLocale == true`, `NavigatorStringCatalog.forLanguageTag(appLanguageTag)` decides *prefixes*; `headingLevelFromStyleName` still scans both packs (so `Judul1` headings remain indexed, but auto-names are English: `Table1`, `Image1`).
* Update `NavigatorStringCatalogTest` to cover both modes rather than asserting Indonesian-only.

This keeps heading *recognition* locale-agnostic while making *labels* policy-driven — satisfying both camps.

## 7. FCT: why a new Papirus doc works but Sample-5 does not

Covered in §3.2 bullet 3, but worth isolating for triage:

* `PapirusTextToolbar` (PapirusTextToolbar.kt:41-85) only shows when `showMenu(rect, onCopyRequested…)` is called — which `BasicTextField` does automatically on selection handles. No handles → no FCT.
* **Viewer path has no selection handles at all** (only `ParagraphText` → `Text()`). Hence “tapping the waterdrop does nothing” is not a bug in FCT, it is a missing selection layer.
* **Editor path for imported docs** has N handles (one per page sheet) but each holds its own `pageTextVal`; focus/selection changes do not update the global `customTextToolbar.rectState` (L≈1070) because `BringIntoViewResponder` was deliberately no-opped to avoid scroll jank (L≈1380).

**Suggestion before coding (P1, ties to §3.4):**

* For Viewer: wrap `LayoutDrivenDocumentRenderer` in `androidx.compose.foundation.text.selection.SelectionContainer` (Compose 1.7) with a `TextActionModeCallback` that delegates to `customTextToolbar`.
* For Editor paginated: collapse to single-model editing (single `docBodyText`) rendered via one selectable viewport rather than per-page `BasicTextField`s — then FCT binding becomes standard.
