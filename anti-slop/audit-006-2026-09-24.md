### 1.2 `Screenshot_…09-46-50` — Editor, same document
* **New:** the per-page counter shows in **Editor** too (`1 / 1` inside the card) — F-01 is mode-independent, exactly as the code reads (`LayoutDrivenDocumentRenderer.kt:174-182`).
* **New (F-21): the toolbar hub shows `14` where the document default is 12.** The new-document caret resolves through `StyleResolver.resolveParagraphStyle(null, styles) → ParagraphStyle("Default", fontSizeSp = 14f)` (`LayoutEngine.kt:61`), while the parser/model default is 12 pt. The same 14 sp is what the paginator measures with, which is why a "blank" document already paginates taller than it should. This is the visible half of the 12-vs-14 split that also drives the DOCX body-size error (F-16).
* **New (F-22): the zoom buttons are 32 dp.** `InkyModule.kt:2439` / `:2454` size the − and + `IconButton`s at 32 dp with 16 dp glyphs. `DESIGN.md:379` — "Strictly Respect 48dp Minimum Touch Targets" — is contradicted, and `AGENTS.md` repeats the 48 dp rule. A 32 dp target is also below the Android accessibility minimum.
* The page card shows a second outer border/grey band around the white sheet (the card's `padding(24dp)` + `background(Color.White)` + `border` combination), which reads as a double frame; cosmetic, but it makes the sheet look inset rather than page-like.

### 1.3 `Screenshot_…10-13-47` — ODT, page 60 of 65 (the table page)
* **F-11 confirmed visually and precisely.** All five columns are equal width (`RenderTable` uses `Modifier.weight(1f)` per cell), so long cell text wraps to one or two words per line and then **breaks mid-word**: "Masyarak / at", "Keterbata / san", "pemaham / an", "meningka / tnya", "Terjangka / unya". Cell text also overflows its row box and collides with the neighbour ("kan" printed over the next cell).
* **New (F-23): the header row's three cells render as three centred paragraphs *above* the bordered table.** The header row's text ("Aksi Konkret", "Tantangan Utama", "Indikator Keberhasilan") is drawn outside the table as standalone centred lines, and the table below starts at the first data row. Cause is one of two, both cheap to test in Plan 7: either the header row was placed on the previous page and its cells were re-emitted as paragraphs, or `table:table-header-rows` paragraphs reach the global element list as well as the cell list (`SvXMLImportContext.kt:418-450` + `OdfTableCellParagraphContext`). Plan 7 must land the parse trace before changing code.
* Per-page counters appear inside both visible cards (F-01 again, on a real document).

### 1.4 `Screenshot_…10-14-31` — ODT, pages 52-53 of 65
* **New (F-24): pages end 40–70 % empty.** Page 53 holds two list items and then ~500 px of dead space before the card ends; 52 holds one line. With `elementGapDp = 12f` (`LayoutEngine.kt:107`) applied to all 547 textual elements plus a fudged 1.9× text metric, the engine is not filling pages to the declared content height; it is flushing early and often. This is the same root as the page-count blow-up, now visible as whitespace rather than only as a number.
* Bullet items show a small `•` followed by normally sized body text — **F-12 confirmed**: the bullet glyph comes from `OdfListItemContext`'s hard-coded string and is not part of the styled run, so it renders at a different size than the item text.
* Body text is justified, italics render (`talanton` on page 17): **the PR C character/paragraph work is visible and correct** for body copy. This is important: the failures are structural (numbering, tables, TOC, metrics), not the character pipeline.

### 1.5 `Screenshot_…10-15-52` — ODT, pages 16-17 of 65
* **New (F-25): page 16 is completely empty.** It renders as a blank sheet with only the redundant `16 / 65` marker. `LayoutEngine` can only produce a page with zero elements through the `OfficePageBreak` path (`LayoutEngine.kt:346-353`), and the renderer's `else -> { }` arm (`LayoutDrivenDocumentRenderer.kt:265`) will silently draw nothing for an element kind it does not handle while still reserving its height. Both mechanisms must be ruled out with a per-page element dump before the metrics fix, otherwise the fix will move the empty pages instead of removing them.
* **F-13 confirmed:** "PEMBAHASAN" renders as a bold centred heading with no `BAB n` prefix; "Konsep Dasar dan Pandangan Alkitab tentang Talenta" and "Definisi dan Etimologi Talenta" render bold and unnumbered. The size hierarchy is present (so heading detection works), the numbering model is absent.
* **F-15 confirmed indirectly:** heading text renders bold because the *heading fallback* style is bold (`LayoutEngine.kt:62-66`), not because the document's heading runs survived — `OfficeDocumentElement.Heading` still has no `runs` field.

### 1.6 `Screenshot_…10-19-39` — DOCX, pages 6-7 of 88 (the TOC)
* **New (F-26): the TOC field code leaks into the document text.** Page 7 begins with the literal line `TOC \o "1 - 9" \z KATA PENGANTAR ii`. That is `w:instrText` being accumulated as body text by the generic pull-parser loop (`OfficeDocumentParser.kt:1030-1036`, TEXT events are appended regardless of container). Field codes must never be rendered.
* **New (F-27): TOC entries have no leader and no separation.** "BAB 1 PENDAHULUAN1", "Rumusan Masalah2", "Manfaat Penulisan2" — the right-aligned page number is glued to the entry text because `w:tab` inside the TOC paragraph is not resolved against the `w:tabs` right-stop with leader. Compare the ODT counterpart, where the same numbers are separated correctly by a `text:tab`.
* **New (F-28): page 6 is a nearly empty page** ("DAFTAR ISI" heading with ~80 % dead space). Same class as F-25; on the DOCX side the TOC's paragraphs were dropped or mis-sized, leaving the heading alone on its page.
* **F-16 confirmed visually:** the TOC entries render at body size with the 14 sp default rather than the `TOC 1/2/3` sizes, and the chapter entries are bold only because the *fallback* heading style is bold. The real DOCX style chain (`w:docDefaults` 12 pt Aptos, `para1` = 20 pt Aptos Display) is still not applied.

## 4. Assessment

The PR C character pipeline did what it promised: sizes, italics, bold and justification are visibly correct in body copy. Everything the screenshots show as *broken* is one of four things, none of them PR C regressions:

1. **Chrome debt** (per-page counters, FAB overlap, 32 dp zoom, 14-sp default chip) — Plan 2.
2. **Measurement and pagination** (empty pages, dead space, 65/88 pages) — Plan 5.
3. **Missing structure models** (numbering, tables, TOC, hyperlinks, heading runs on the ODF side; the whole style chain and numbering on the OOXML side) — Plans 7 and 8.
4. **Write-path integrity** (dangling style references, dropped page breaks, flattened lists, `[Image: path]` substitution, unmanifested images) — Plans 6 and 9.

The compliance sweep adds one systemic conclusion: the project's own rule "**non-destructive package preservation**" is honoured on the ODT side only when the document is unmodified, and not at all on the DOCX side. Until Plan 9, the safe product decision is to warn before saving an edited DOCX and to keep the original package bytes alongside the rewrite.
